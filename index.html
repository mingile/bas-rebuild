구현 내용 HTML5 웹뷰로 직접 개발

  • 플랫폼 기본 화면은 폴더형 네비게이션 트리라 건물이 많으면 찾기 어려웠습니다. 전용 유료 모듈 대신, 외부 벤더 종속을 줄이라는 회사 방침에 따라 웹뷰로 직접 만들었습니다.
  • 직접 구현 건물번호 자동완성 검색 — 라이브러리 없이 부분 일치 필터링과 방향키·Enter 키보드 탐색
  • 직접 구현 지도 위 마커 표시 — 건물별 좌표를 모아 건물번호를 id로, CSS top/left로 배치. 지도 영역을 고정 크기로 두어 화면 크기와 관계없이 위치 유지

구현 내용 플랫폼 그래픽 에디터로 구성

  • 건물마다 설비 배치와 포인트 바인딩이 모두 달라 공통 화면 하나로 처리할 수 없었습니다. 그래서 건물 홈과 메뉴를 건물 단위로 각각 설계하고 구성했습니다.
  • 화면 설계 건물 홈 — 건물 전경과 기본 정보(용도·규모·연면적·준공·공조기 대수)를 한 화면에 배치해, 관제 화면에 들어오자마자 어떤 건물을 보고 있는지 알 수 있게 구성
  • 템플릿 활용 상단 메뉴 — 기본 메뉴 템플릿을 바탕으로, 건물마다 다른 설비 구성에 맞춰 메뉴 항목을 화면별로 다르게 적용
  • 직접 구현 알람 버튼 — 알람 콘솔은 플랫폼 기본 기능을 활용하고, 메뉴 바의 알람 버튼이 알람 발생 여부(이벤트)에 따라 동적으로 바뀌도록 구현. 운영자가 어느 화면에 있든 알람 발생을 바로 알아챌 수 있게 했습니다.

구현 내용 플랫폼 그래픽 에디터로 구성

  • 화면 설계 건물별 도면과 HVAC 다이어그램을 기준으로 설비를 배치해, 건물마다·설비마다 서로 다른 AHU 화면을 각각 설계
  • 직접 구현 설비 상태 표현 — 플랫폼 기본 이미지에 포토샵으로 편집한 이미지를 더해 쓰고, 설비 상태에 따라 이미지가 바뀌는 로직과 애니메이션(팬 회전, 댐퍼 열림·닫힘 등)을 직접 구현
  • 직접 설정 포인트 상태 표시 — 값 이상·알람뿐 아니라 네트워크 상태(응답 없음, 응답은 있으나 정상 아님)까지 배경색으로 구분해, 운영자가 설비 문제와 통신 문제를 한눈에 구별할 수 있게 구성
  • 운영 기능 운전/정지 명령, 설정값(setpoint) 변경, 알람 표시를 화면에서 바로 할 수 있게 구성
  • 직접 구현 가상 포인트 — 기존 데이터 포인트만으로는 구현할 수 없는 화면 로직을 위해 가상 포인트를 새로 만들어 연결

구현 내용 플랫폼 히스토리 뷰 활용

  • 화면 구성 프로젝트 전용으로 만든 건물 화면 안에 히스토리 뷰를 배치하고, 상단 메뉴의 TREND 버튼 하나로 진입하도록 구성
  • 수집 설정 계약 시 정한 포인트(온도, 풍량, 연기 감지, 동결 감지 등)를 정해진 기준(15분 간격)에 맞춰 트렌드로 기록하도록 설정
  • 플랫폼 활용 기간 선택, 여러 포인트 겹쳐 보기, 데이터 내보내기는 플랫폼 기본 히스토리 뷰 기능을 그대로 활용

2. 자동화 파이프라인 재구성 준비 중

구현 내용 Python

  • 문제 발견 데이터베이스 팀이 엑셀로 넘긴 바인딩 정보를 팀원들이 플랫폼 안에서 XML 기반 포인트 매핑으로 일일이 옮기고 있었습니다. 단순 반복이라 시간이 많이 들고 실수가 잦았습니다.
  • 직접 구현 건물별 포인트 주솟값의 규칙성을 찾아, 엑셀에서 필요한 데이터만 파싱해 XML을 일괄 생성하는 Python 도구 제작. 산출물은 포인트 매핑 · 히스토리 · 알람 · 단위 변환 용도별로 분리
  • 팀 배포 tkinter로 GUI를 만들고 exe로 패키징해 팀원 3~6명이 Python 설치 없이 바로 쓰도록 배포
  • 지속 개선 규칙에 맞지 않는 예외 데이터는 팀원들이 노션과 Slack에 건물과 내용을 올리면 도구에 반영. 모든 건물 유형을 파악한 프로젝트 후반부에는 프로젝트 범위 안에서 오류 없이 안정적으로 적용
  • 성과 3번의 포인트 일괄 삽입 컴포넌트와 이어지는 전체 흐름으로, 포인트 1,000개 기준 작업 시간 2일 → 0.5일. 향후 견적 산정을 위해 팀 작업 기록으로 포인트별 소요 시간을 실제로 계산한 결과

  • 직접 구현 DDC 제어 로직 모듈 — 기존 DDC(JCI) 제어 로직을 플랫폼에서 재현하려면 수십 개의 노드를 서로 연결해야 했습니다. 이를 Java로 구현해 노드 1개로 대체(로직 자체는 기존 시스템의 것을 사용)

4. 데이터 연동재구성 준비 중

구현 내용 MQTT · MySQL

  • 테스트 MQTT 연동 — 스마트서버 IoT 장비의 상태와, 장비에 연결된 DDC들의 포인트 데이터를 BACnet 외에 MQTT로도 받아오도록 연결하고, 이를 보여 주는 커스텀 웹페이지를 제작. 관제 플랫폼을 쓸 수 없는 현장에 대비해 대안을 검증한 테스트로, 실사용은 하지 않았습니다.

1기록은 로컬이 기준, Notion은 동기화 대상

localStorage를 단일 출처(SSOT)로 두고 Notion DB를 선택적 동기화 계층으로 분리했습니다.

외부 서비스가 장애여도 기록 저장 자체는 막히지 않도록 의존 방향을 정했습니다.

2기다리지 않는 저장

운동을 마치고 Notion에 저장할 때 응답이 올 때까지 앱을 켜 두고 기다려야 했습니다. 요청 이후 처리를 서버 쪽 큐로 분리하고, 재시도·ack와 멱등 키로 중복 쓰기를 막았습니다.

3캐시 전략을 대상별로 분리

Service Worker에서 app shell은 cache-first, 외부 연동 상태 API는 캐시를 우회하게 했습니다.

오래된 상태 값 때문에 동기화가 잘못 일어나는 것을 막기 위해서입니다.

4Next.js를 고른 이유

Notion API는 클라이언트에서 직접 부를 수 없어 서버 쪽 코드가 필요했고, 서버리스로 설정 없이 무료 호스팅을 하고 싶었습니다. Vitest 단위 테스트를 두고 Vercel에 배포했습니다.
